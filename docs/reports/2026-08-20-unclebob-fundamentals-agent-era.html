The whole conversation in one paragraph

Robert C. Martin argues that software fundamentals survive the agent era but their enforcement mechanisms don't: clean code still matters because agents choke on mess just as humans do, yet prompt-based steering (long CLAUDE.md files) decays as context grows. So Bob has moved nearly all quality enforcement into deterministic post-hoc gates — CRAP complexity-×-coverage scoring, mutation testing, dependency checkers — run by a five-stage pipeline of ephemeral single-purpose agents (specifier → coder → cleaner → hardener → QA), with the radical goal of never reading agent code at all. He retunes his own canon on the way: strict TDD is a human-wiring discipline agents shouldn't be forced into (the values — full coverage, every mutant killed — transfer intact), complexity thresholds loosen from 4 to 6–8, upfront planning with agents fails like 1970s waterfall because the cost of change has collapsed, and persisted spec-driven development "probably won't work" since the end result is the specification. Humans stay irreplaceable for architecture, for recognizing agent thrash, and for growing juniors — who should be "treated like an agent" but still write code for a year first. Matt supplies the mechanistic framing — lost-in-the-middle, context trajectory, TDD as memory compensation — and pushes back on multi-agent scale and on eliminating human review.

Disciplines are human wiring; values transfer

  • Bob 31:30–35:45 — The biggest TDD advocate alive now says forcing strict red-green-refactor micro-stepping on agents is a mistake: they always fall back to write-function-then-test even when ordered otherwise, and he lets them. The values behind TDD — tests exist, coverage complete, mutants dead — transfer fully; the ceremony does not.

  • Matt 31:30–35:45 — Reframes why: TDD compensated for tiny human short-term memory; agents have huge, accurate short-term memory, so the compensation is unnecessary. Bob accepts the framing.

"It's probably a mistake to impose a human discipline on an agent… It is not a mistake to impose human values on the agent."— Bob

Durability belongs in executable artifacts — tests, Gherkin, QA scripts, dependency rules — not prose.

What this means for a team like ours

We already run interview-first planning, spec → tickets → implement, TDD, and two-axis code review. This conversation confirms some of it and challenges the rest.

  1. Slim the steering layer. Audit skill files and CLAUDE.md for encyclopedic rules; cut to the minimum, and pair each cut rule with a mechanical check (linter, coverage gate, custom analyzer) that enforces it after the fact. Long standing prompts decay; gates don't.

  2. Add a mutation-testing + complexity gate as a required agent-run loop — "change the code until the tool says okay" — not a human chore. Build it bespoke: point agents at Bob's published tools as reference and generate a stack-specific version.

  3. Make architecture a human deliverable with machine enforcement. A per-repo dependency-rules spec file plus a checker that fails the build on violations. Don't delegate module partitioning to agents.

  4. Retune the TDD skill to enforce outcomes, not ceremony. Tests exist, coverage complete, mutants dead — but stop forcing red-green micro-stepping on agents, and consider relaxing per-function complexity thresholds where coverage is total.

  5. Treat specs as disposable inputs. Keep tickets small, re-plan between them, and invest durability in executable artifacts — acceptance tests, QA scripts, dependency rules — instead of prose nobody reads.

  6. Design junior onboarding as gauntlet-first apprenticeship. A real year of hands-on coding, then months inside the same pipeline and gates as the agents — and keep enough hands-on coding in every engineer's diet that thrash-recognition doesn't atrophy.
