The Pocock Loop

A repeatable pipeline for agent coding: four routes, one routing question, and the context-window rules that hold it together.

Source: mattpocock/skills v1.2.3 · the Aug 14 video (10:18, ~261K views) · aihero.dev

The two-minute version

Matt Pocock — the TypeScript educator behind Total TypeScript — posted a ten-minute video walking through all 25 skills in his open-source AI coding workflow (github.com/mattpocock/skills, MIT). It took off after Theo from t3.gg endorsed the interview skill: "helps a ton with getting agents aligned with my brain."

The core idea: an agent left to guess writes plausible code that quietly rots a codebase. So instead of prompting ad hoc, you run a fixed pipeline of skills — small instruction packages — where each one's output is the next one's input. Tune one step and the whole chain improves.

The spine is five skills, in order. grill-with-docs: the agent interviews you, one question at a time, until you share one understanding — decisions land in the repo as a glossary and decision records. to-spec: turns that finished conversation into a written spec; no new decisions allowed. to-tickets: cuts the spec into small vertical-slice tickets, each buildable in one fresh agent session. implement: builds one ticket, test-first, no debating. code-review: checks the diff against repo standards and against the spec, separately.

Around the spine sit shaping tools for before you know what to build (wayfinder maps a big foggy effort as decision tickets you settle one session at a time; prototype answers a design question with throwaway code; research fetches cited answers), upkeep tools (bug diagnosis, triage for incoming issues, merge-conflict resolution, a periodic architecture health check), and session tools (handoff writes up a session so another agent or colleague can continue it).

Why it matters for us: this is the most complete public answer to the question we keep hitting — how do you make agent coding repeatable instead of vibes? The skills are free and install as a Claude Code plugin in one command; we already run a subset internally. His paid Crash Course teaches the concepts behind them, but the skills and the per-skill articles on aihero.dev cover most of it.

Habit 1 — make the agent interview you first

Misalignment is the expensive failure. Ten minutes of being grilled before any code costs less than one wrong afternoon of plausible-looking output.

Habit 2 — size work to one fresh session

Agents degrade as context fills. Every ticket is cut to fit a single clean context window, and gets one.

The routing question

Session count, not project size

Every piece of work enters through one question: how many agent sessions does it need? Not "is this a big project" — sessions.

SituationRoute
No working directory yet/grill-me — same interview, no paper trail
Design question needing runnable codeprototype detour on a prototype/* branch; always deleted from main
Bug report or request from someone else/triage — merges into the flow at ready-for-agent
Hard bug / perf regressiondiagnosing-bugs — phase 1 builds a red-capable feedback loop; that is 90% of the fix
Unsure which path/ask-matt — recommends the next thing to type, then stops

Path A · single-session feature

Grill, then build — no spec, no tickets

What it writes down

Domain terms go into CONTEXT.md as they resolve. An ADR only when a decision passes all three gates: hard to reverse, surprising, and a real trade-off. Zero ADRs is a valid outcome.

When not to use it

The build needs more than one session (B), the route itself is foggy (C), the issue came from someone else (/triage), or the change is trivial — then just do it.

Path B · multi-session build

Decide once, write it down once, execute per ticket

The spec is a record

"A record of decisions already made, not a place where new ones get made." to-spec never re-interviews; it sketches testing seams first (ideal count: one) and publishes a single tracker issue.

Tickets are tracer bullets

Vertical slices through schema, API, UI, tests — each independently demonstrable, each sized to one context window, blocking edges declared. Wide refactors get expand–contract sequencing.

Known gap

implement ends at the commit and never closes the ticket. Close it yourself, or downstream tickets never visibly unblock.

Never in parallel

One checkout, one implement at a time. Parallel implements in the same working copy corrupt each other's assumptions.

Path C · foggy, huge efforts

Map the decisions before anyone plans the build

The map is shared state

A tracker issue (wayfinder:map) holding the destination, decisions so far, remaining fog, and out-of-scope — plus one child ticket per open decision, with blocking edges.

One decision per session

Pick one frontier ticket — open, unblocked, unclaimed. Resolve it with the matching skill, post the resolution, close it, add one line to the map. Research tickets are the only exception; they run AFK in parallel.

Path D · phase boundaries

Five continuations, in strict order

At every boundary between phases — grilling done, ticket shipped, QA starting — or when context nears the ~150k smart zone, walk this list top to bottom and take the first option that fits. /compact is the default; /handoff is the exception.

  1. Continue

    Only when the next phase needs the current context verbatim — the one move that keeps the session a primary source. Rule it out first.

  2. /clear

    Everything behind you is disposable. The move between implement tickets.

  3. /handoff

    Only when work must travel — exactly four triggers: new harness, new directory or repo, a colleague, or forking a side task mid-phase. Writes one markdown file to the OS temp dir; references specs and ADRs by path, never copies them. Review it and downgrade unverified assumptions before handing it over. It buys portability, not compression.

  4. Subagent

    Tightly scoped, unattended work that shouldn't pollute the main session.

  5. /compact

    The default fallback: same harness, same directory, same person, phase done. Compact at boundaries, never mid-phase.

The one hard rule: grill-with-docs → to-spec → to-tickets share one unbroken context. Never /clear or /compact between them.

Sharp edges, from the author's own docs

  • implement never closes its ticket — close it manually or blocked tickets never visibly unblock.
  • /ask-matt falsely reports slash-only skills as "not installed" — the harness omits them from its injected list.
  • grill-with-docs file-writing silently fails when wrapped in another orchestration layer — run it directly.
  • Dead names still floating around older articles: /to-prd → to-spec, /to-issues → to-tickets, /diagnose → diagnosing-bugs.
  • Once per repo, before any of this: /setup-matt-pocock-skills — tracker choice, triage labels, domain-doc layout.
